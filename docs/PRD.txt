# AuthShield — Product Requirements Document (PRD)

**Version:** 1.0
**Status:** Planned
**Primary goal:** Demonstrate practical understanding of authentication, authorization, IAM, security monitoring, audit logging, and backend engineering.

---

## 1. Product Overview

### Product Name

**AuthShield**

### Product Type

Security-focused REST API and identity monitoring platform.

### One-line description

> **AuthShield is a security-focused backend that provides JWT authentication, role-based access control, audit logging, and rule-based detection of suspicious authentication and authorization activity.**

### Problem

Applications commonly implement authentication but have limited visibility into what happens **after and around authentication**.

For example:

* Who logged in?
* Was the login successful?
* Where did the request originate?
* Who accessed a protected resource?
* Who attempted an unauthorized action?
* Did someone suddenly receive elevated privileges?
* Are repeated failed logins occurring?
* Was a disabled account attempting to authenticate?

AuthShield combines **identity management and security monitoring** into one small, understandable system.

# 5. Roles & Permissions

AuthShield initially uses three roles.

| Role      | Description                            |
| --------- | -------------------------------------- |
| `user`    | Regular application user               |
| `analyst` | Security monitoring/investigation user |
| `admin`   | System administrator                   |

### Example permission model

| Action               | User | Analyst | Admin |
| -------------------- | ---: | ------: | ----: |
| View own profile     |    ✅ |       ✅ |     ✅ |
| Update own profile   |    ✅ |       ✅ |     ✅ |
| View security alerts |    ❌ |       ✅ |     ✅ |
| View audit logs      |    ❌ |       ✅ |     ✅ |
| Investigate alerts   |    ❌ |       ✅ |     ✅ |
| View users           |    ❌ | Limited |     ✅ |
| Disable user         |    ❌ |       ❌ |     ✅ |
| Change roles         |    ❌ |       ❌ |     ✅ |
| Manage permissions   |    ❌ |       ❌ |     ✅ |

The authorization layer should enforce these permissions **server-side**.

The frontend should never be trusted to enforce access control.

# 6. Core Functional Requirements

## FR-01 — User Registration

The system shall allow a user to create an account.

### Required information

```text
username
email
password
```

### Requirements

* Email must be unique.
* Username must be unique.
* Password must never be stored in plaintext.
* Password must be securely hashed.
* New users receive the default `user` role.
* Registration should generate an audit event.

Example:

```text
USER_REGISTERED
```

---

# 7. Authentication

## FR-02 — Login

Users shall authenticate using:

```text
email + password
```

On successful authentication:

```text
User
 ↓
Password verification
 ↓
Authentication successful
 ↓
JWT generated
 ↓
Client receives access token
```

The JWT should contain appropriate identity information such as:

```text
user_id
role
expiration
```

Do **not** put sensitive information such as passwords into the JWT.

---

## FR-03 — JWT Validation

Protected endpoints must validate the JWT.

Requests without a valid token should receive an appropriate authentication error.

Examples:

```text
Missing token
Expired token
Malformed token
Invalid signature
```

Each relevant event should be logged.

---

# 8. Authorization

Authentication answers:

> **Who are you?**

Authorization answers:

> **What are you allowed to do?**

AuthShield must keep these concepts separate.

Example:

```text
Authenticated User
        ↓
JWT validated
        ↓
User identity determined
        ↓
Role determined
        ↓
Permission checked
        ↓
Resource accessed
```

A valid JWT alone must **not** automatically provide administrative access.

---

# 9. RBAC

## FR-04 — Role-Based Access Control

The system shall restrict API operations according to the user's role.

Example:

```text
GET /alerts
```

Allowed:

```text
analyst
admin
```

Denied:

```text
user
```

The system should record unauthorized attempts.

Example event:

```text
ACCESS_DENIED
```

# 12. IP Monitoring

AuthShield should record the source IP associated with security events.

The goal isn't to perform advanced network forensics.

Instead, IP information provides **context for security events**.

For example:

```text
User: varun
IP: 10.0.0.15
LOGIN_FAILED

User: varun
IP: 10.0.0.15
LOGIN_FAILED

User: varun
IP: 10.0.0.15
LOGIN_FAILED
```

This information can then be consumed by the detection engine.

### Important

Development/testing should support simulated IP addresses so you can test detection without needing multiple physical devices.

# 13. Security Detection Engine

This is where AuthShield becomes more than a normal authentication API.

The detection engine analyzes security events and generates alerts when predefined rules are triggered.

Initially, use **rule-based detection**, not machine learning.

---

## Detection Rule 1 — Brute Force

### Condition

If:

```text
5 failed login attempts
FROM same IP
WITHIN 5 minutes
```

generate:

```text
BRUTE_FORCE_LOGIN
```

Example:

```text
10:00 → Failed
10:01 → Failed
10:02 → Failed
10:03 → Failed
10:04 → Failed
             ↓
        🚨 ALERT
```

---

# 14. Detection Rule 2 — Repeated Unauthorized Access

If a user repeatedly attempts to access an endpoint they don't have permission to access:

```text
ACCESS_DENIED
ACCESS_DENIED
ACCESS_DENIED
ACCESS_DENIED
```

the system can generate:

```text
REPEATED_UNAUTHORIZED_ACCESS
```

The exact threshold can be configurable.

---

# 15. Detection Rule 3 — Privilege Escalation

If an administrator changes:

```text
user → admin
```

generate an audit event:

```text
ROLE_CHANGED
```

and optionally generate:

```text
PRIVILEGE_CHANGE
```

security alert.

This is useful because unexpected role changes are security-sensitive events.

---

# 16. Detection Rule 4 — Disabled Account Login

If an account is disabled:

```text
user.status = disabled
```

and someone attempts to log in:

```text
LOGIN_ATTEMPT_DISABLED_ACCOUNT
```

should be recorded.

Depending on your implementation, this can generate a security alert.

# 18. Alert Severity

Initially:

```text
LOW
MEDIUM
HIGH
CRITICAL
```

Example mapping:

| Event                              | Severity |
| ---------------------------------- | -------- |
| Single failed login                | LOW      |
| Repeated unauthorized access       | MEDIUM   |
| Brute-force pattern                | HIGH     |
| Suspicious privilege change        | HIGH     |
| Disabled account repeated attempts | HIGH     |

These are **project-defined rules**, not claims that these severities are universal industry standards.

# 24. Security Requirements

AuthShield itself should follow basic secure-development principles.

### Passwords

Never:

```text
password = "mypassword123"
```

stored in database.

Instead:

```text
password
   ↓
secure hash
   ↓
password_hash
```

---

### Authentication

JWTs should:

* Have an expiration time.
* Be cryptographically signed.
* Be validated on protected requests.
* Not contain sensitive secrets.

---

### Authorization

Never rely on:

```text
role="admin"
```

sent by the client.

The server must determine the authenticated user's role from trusted server-side data.

---

### Input Validation

FastAPI/Pydantic validation should be used for incoming data.

---

### Error Handling

Avoid exposing unnecessary internal information.

For example, don't return:

```text
PostgreSQL connection failed at /app/database/connection.py line 42...
```

to an ordinary API client.

## The core principle

**Don't try to make AuthShield huge. Make it defensible.**

If an interviewer asks:

> "How does your brute-force detection work?"

You should be able to open the code and explain it.

If they ask:

> "What's the difference between authentication and authorization?"

You should be able to explain it immediately.

If they ask:

> "Why did you use RBAC?"

You should have a clear answer.

If they ask:

> "How did you test multiple IP addresses?"

You should be able to show the automated simulation.

If they ask:

> "What happens when a normal user calls an admin endpoint?"

You should be able to demonstrate:

```text
JWT → identity → role → permission → DENIED → audit log
```

**That's the level of project I would target for your Cyderes application.**
